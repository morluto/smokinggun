# Literature matrix and gap analysis

The reading set covers four different evidence levels: static code
classification, dynamic complexity inference, function/program optimization,
and repository-level patch evaluation. They should not be collapsed into one
score. A classifier can recognize a pattern without proving its cost, and a
benchmark can show a speedup without explaining which static signal would have
found the bottleneck.

| Work | Granularity and data | Measurement method | Important assumptions or failure modes | Directly applicable idea |
| --- | --- | --- | --- | --- |
| [BigO(Bench, 2503.15242)](https://huggingface.co/papers/2503.15242) | Python functions; 3,105 problems and 1,190,250 Code Contests solutions | Generates expanded inputs, executes sandboxed runs, measures runtime with `cProfile` and memory with `tracemalloc`, then fits candidate complexity curves with non-negative least squares | Empirical worst-case depends on input expansion, selected curve classes, timeouts, and Python/CPython behavior. It is not a repository call graph and does not model external I/O. The reported match to human theoretical labels is 92% for time and 84% for space on its test sets, not a guarantee for arbitrary code. | Use profiling and curve fitting to validate or reject a static estimate; retain the measured curve, residual, input-growth rule, and confidence rather than emitting an unqualified `O(...)`. |
| [TASTY, 2305.05379](https://huggingface.co/papers/2305.05379) | Code-snippet classification; labeled Python and C++ datasets from GeeksforGeeks plus Java CodeComplex comparisons | Fine-tunes BERT-family code models to classify time and space classes; averages results across five runs | Dataset classes are imbalanced and dominated by linear/quadratic examples; labels and code source are narrow; classification does not prove behavior on repository workloads; sequence length truncation and dead-code removal affect the task. | Keep a labeled, multi-language corpus for precision/recall and use learned models, if at all, as a supplementary ranking signal rather than a proof mechanism. |
| [Learning Performance-Improving Code Edits / PIE, 2302.07867](https://huggingface.co/papers/2302.07867) | C++ competitive-programming programs; 77,967 training slow/fast pairs, with correctness tests and held-out problems | Relabels runtime in a deterministic gem5 environment; keeps edits over a 10% improvement threshold; rejects candidates failing tests; evaluates `%Correct`, `%Opt`, and speedup | Competitive-programming code and C++ do not represent service or repository behavior. Test adequacy still bounds functional equivalence. gem5 reduces hardware noise but is expensive and models a chosen processor configuration. | Store before/after trajectories, correctness outcomes, workload identity, and a performance threshold; require both functional equivalence and measured improvement. |
| [SWE-Perf, 2507.12415](https://huggingface.co/papers/2507.12415) | Repository-level; 140 instances from performance-improving pull requests across nine repositories | Builds Docker environments, runs performance-related unit tests three times, filters for stable statistically significant gains, and evaluates oracle/file-level and realistic/repository-level agents against expert patches | Only nine repositories and targeted functions are covered; the expert patch is evidence that an improvement exists, not the global optimum; targeted tests may omit important workloads; runtime remains environment-sensitive. | Add repository context, callers, tests, and executable workloads to static findings; separate “can find a candidate” from “can improve this repository.” |
| [GSO, 2505.23671](https://huggingface.co/papers/2505.23671) | Repository/system-level; 102 tasks across 10 codebases, five languages, and eight domains | Mines commit histories, generates performance tests with execution-based rejection sampling, manually curates tasks, checks correctness, and compares patches with harmonic-mean speedup using `Opt_p@K` against a human target | Generated tests can be weak or gameable; agents often mislocalize bottlenecks or make superficial changes; human targets are not necessarily optimal; low-level and cross-file work is difficult. | Use workload-based tests as the task specification, harmonic aggregation to reduce outlier gaming, and explicit anti-cache/anti-input-overfit checks. |
| [How Do Agents Perform Code Optimization?, 2512.21757](https://huggingface.co/papers/2512.21757) | 407 performance PRs: 324 agent-authored and 83 human-authored, mined from AIDev | LLM-assisted catalog labeling with human adjudication; classifies benchmark-, profiling-, static-, and anecdotal validation reported in PR artifacts | Validation is self-reported, not direct trace evidence. The study finds explicit validation in 45.7% of agent PRs versus 63.6% of human PRs, and agents rely more on static reasoning. Dataset labels, repository mix, and PR documentation introduce selection and measurement bias. | Make benchmark/profiling evidence a first-class report field and do not treat a static explanation as empirical validation. |
| [Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?, 2607.01211](https://huggingface.co/papers/2607.01211) | Audit of 740 tasks from GSO, SWE-Perf, and SWE-fficiency | Replays reference patches across four Google Cloud machine types and three rounds; audits scoring rules and public submissions | Reference validity is not stable across machines: only 39/102 GSO, 11/140 SWE-Perf, and 411/498 SWE-fficiency tasks passed every replay rule. Scores can be dominated by benchmark-specific aggregation and a few tasks. The study covers selected public benchmarks, not all optimization workloads. | Record machine, environment, repetition, raw samples, validity rule, and scoring function. Report per-task distributions and cross-machine stability, not only one aggregate speedup. |

## Additional research for a redesign

The initial reading set is useful for evaluation design. The papers below add the
missing theory, profiling, and current repository-scale evidence needed to
decide what the scanner should become.

| Work | Granularity and method | Assumptions or failure modes | Directly applicable idea |
| --- | --- | --- | --- |
| [A Simple and Scalable Static Analysis for Bound Analysis and Amortized Complexity Analysis, 1401.5842](https://arxiv.org/abs/1401.5842) | Derives bounds from abstract program models built with invariant generation and symbolic execution; uses ranking functions and lossy vector addition systems. | Static bound analysis needs a restricted model and sound invariants; dynamic dispatch, external effects, and unsupported constructs become unknown rather than magically solvable. | Treat formal bounds as an optional proof backend over a declared subset, with a proof artifact and an explicit “not analyzed” result. |
| [Denotational recurrence extraction for amortized analysis, 2006.15036](https://arxiv.org/abs/2006.15036) | Extracts recurrences for functional programs and extends the method to amortized cost. | Recurrence extraction depends on a suitable language semantics and correct cost model; it is not a general repository profiler. | Model recursive and divide-and-conquer candidates as recurrence hypotheses instead of labeling every recursive call as exponential or linear. |
| [Non-polynomial Worst-Case Analysis of Recursive Programs, 1705.00317](https://arxiv.org/abs/1705.00317) | Uses ranking-function techniques to derive bounds for recursive algorithms including merge sort, closest pair, Karatsuba, and Strassen. | Recursive bound inference is substantially harder than detecting self-calls; input measures, branching, and recurrence solving must be justified. | A `recursive-call` finding should ask for a recurrence/input measure and never infer a bound from recursion syntax alone. |
| [Automatic Amortized Resource Analysis with Regular Recursive Types, 2304.13627](https://arxiv.org/abs/2304.13627) | Uses resource polynomials and type inference to infer symbolic resource bounds over recursive data structures. | Type-based automation has an incompleteness boundary and assumes a typed core language with a defined operational cost model. | Collection/type facts can raise confidence locally, but only a typed semantic backend should claim a symbolic resource bound. |
| [Robust Resource Bounds with Static Analysis and Bayesian Inference, PLDI 2024](https://www.cs.cmu.edu/~longp/publication/hybrid-aara/) | Combines type-based Automatic Amortized Resource Analysis with Bayesian inference over measured costs; reports a distribution of likely resource bounds rather than one unsupported point estimate. | Static analysis is sound but incomplete; data-driven inference is more complete but not automatically sound. Statistical soundness depends on the model, data, and assumptions. | Make static and empirical evidence composable but visibly different: a measured posterior can fill an unknown fragment, while only a proof backend may claim soundness. |
| [Integrating Resource Analyses via Resource Decomposition, OOPSLA 2025](https://doi.org/10.1145/3763798) | Defines resource components as an interface between static, data-driven, and manual analyses; composes bounds with a soundness argument and evaluates several instantiations. | Composition is only sound when the component interfaces, cost semantics, and substitutions are valid. It remains a research framework, not a language-agnostic repository tool. | Represent evidence fragments and their composition boundary explicitly. A hybrid report should show which code was proved, measured, or manually modeled instead of flattening them into one confidence score. |
| [Analyzing Program Termination and Complexity Automatically with AProVE](https://www.microsoft.com/en-us/research/publication/analyzing-program-termination-complexity-automatically-aprove/) | Translates supported Java, C, Haskell, Prolog, and rewrite systems into rewrite representations, applies termination/complexity techniques, and can export independently checkable proofs. | Supported-language/model coverage and analysis time are bounded; failure or timeout means unknown, not “efficient.” Proofs apply to a declared cost model and abstraction. | Treat certified complexity as an optional proof artifact with `proved`, `unknown`, `timeout`, and cost-model metadata. AProVE is a useful reference for result contracts. |
| [Resource Analysis in the COSTA System](https://logicprogramming.org/2012/12/resource-analysis-in-the-costa-system/) | Builds cost relations and solves them for upper/lower bounds over Java-like programs and multiple resources, including instructions, heap allocation, and billable events. | COSTA is a research prototype and its language/cost-model coverage is not a general mixed-language repository solution; relation solving can be difficult or incomplete. | Make “resource” explicit—time, allocations, instructions, events, parallelism—rather than treating runtime as the only complexity axis. |
| [A Problem-Oriented Perspective and Anchor Verification for Code Optimization, 2406.11935](https://huggingface.co/papers/2406.11935) | Reconstructs optimization trajectories across different solutions to the same problem; creates verified test anchors by executing generated inputs against trusted slow code. | Competitive-programming data and model-generated tests do not cover repository side effects; execution-derived anchors are only as good as the input distribution. | Keep a trusted baseline/oracle, generate candidate inputs, execute the baseline to obtain expected outputs, and use those anchors during optimization validation. |
| [SysLLMatic: Large Language Models are Software System Optimizers, 2506.01249](https://huggingface.co/papers/2506.01249) | Uses a diagnosis cycle of hypothesis, instrumentation, and data collection, with system-level metrics beyond runtime. | System-level measurements are hardware- and workload-dependent; the paper's broad claims span domains that the small scanner cannot cover directly. | Make diagnosis iterative and multi-objective: runtime, memory, energy, and maintainability are separate objectives with explicit trade-offs. |
| [SWE-fficiency, 2511.06090](https://huggingface.co/papers/2511.06090) | 498 repository-level tasks with annotated workloads, correctness tests, containerized environments, and an expert-relative speedup ratio aggregated harmonically. | The workload is curated and repository-specific. The study reports that more than 68% of expert gains were in functions the agent did not edit, and that manually annotated workloads outperformed generated workloads in 76% of comparisons; these are benchmark observations, not universal rates. | Add call-path/function attribution and workload quality checks. Candidate discovery must reduce mislocalization, not merely produce more warnings. |
| [ISO-Bench, 2602.19594](https://huggingface.co/papers/2602.19594) | 54 inference-optimization tasks from vLLM and SGLang; combines hard performance deltas with soft target-identification judgments and a four-quadrant success framework. | Hardware-specific GPU results and LLM-as-judge labels introduce domain and evaluator dependence; a speedup can be a “lucky win” unrelated to the intended bottleneck. | Report target correctness separately from speedup. A measured improvement on the wrong path should not upgrade the original finding's confidence. |
| [FormulaCode, 2603.16011](https://huggingface.co/papers/2603.16011) | 957 bottlenecks across 70 scientific Python repositories, paired with expert patches and an average of 264.6 community workloads per task; evaluates multi-objective workload trade-offs. | Community workloads vary in coverage and noise; repository popularity and project conventions affect results. A single workload win can regress another. | Use a workload family and a Pareto-style report rather than a single benchmark number; retain per-workload ratios and regressions. |
| [PERFOPT-Bench, 2607.07744](https://huggingface.co/papers/2607.07744) | 12 long-horizon tasks across toolchain, SIMD, memory/cache, parallelism, and algorithmic restructuring; requires hidden correctness, verified speedup, and trajectory audit. | The paper explicitly cautions that speedups are environment-conditioned and its single-run cells are descriptive rather than statistically stable; shortcut exploitation remains difficult to classify automatically. | Treat speedup as a claim bound to hardware, compiler/runtime, inputs, and audit status. Add anti-overfitting checks and preserve the measurement trajectory. |
| [Fully Symbolic Analysis of Loop Locality: Using Imaginary Reuse to Infer Real Performance, 2603.10196](https://arxiv.org/abs/2603.10196) | Derives symbolic locality polynomials for affine loop nests and predicts cache misses across input sizes/configurations; evaluates 41 scientific kernels and tensor operations against simulated L1 caches. | The method targets affine loops and a cache model; it does not cover dynamic dispatch, external I/O, arbitrary runtimes, or full application performance. The reported 99.6% prediction accuracy is benchmark- and model-specific. | Keep cache/data-movement analysis as a specialized backend with explicit hardware/cache assumptions, not a general replacement for timing or profiling. |
| [Finding Performance Issues in Database Systems by Exploiting Dormant Code Paths, 2605.22992](https://arxiv.org/abs/2605.22992) | Branch Flip Analysis disables/enables optimizer branches to create a fine-grained differential performance oracle; QueryZen found 21 unique performance issues across four DBMSs using TPC-H/TPC-DS workloads. | It requires white-box access and meaningful optimization branches; a branch flip can alter more than the targeted behavior, and database benchmark coverage does not equal application coverage. | Add differential “optimization enabled/disabled” experiments when a system exposes a safe switch. This can validate bottleneck causality beyond passive profiling. |
| [Detecting Optimization Bugs in Database Engines via Non-Optimizing Reference Engine Construction, NoREC](https://arxiv.org/abs/2007.08292) | Rewrites optimized SQL into a semantically equivalent form that prevents the DBMS optimization, then compares result sets; evaluated across PostgreSQL, MariaDB, SQLite, and CockroachDB. | The oracle targets DBMS optimizer correctness, not application performance; query rewriting has coverage limits and result equivalence does not establish comparable speed. | Preserve the distinction between correctness oracles and performance oracles. For query rewrites, first obtain a trusted result-set oracle, then measure plans and latency separately. |
| [SWE-PolyBench, 2504.08703](https://huggingface.co/papers/2504.08703) | 2,110 repository-level execution-based tasks from 21 repositories across Java, JavaScript, TypeScript, and Python; includes an automated harness and syntax-tree metrics. | It is a broad repository/code-agent benchmark rather than a performance-specific oracle; language mix and task types do not establish complexity or speedup validity. | Use it as a reference for multi-language repository harnesses and stratified reporting, while keeping optimization evidence separate from general code-task pass rates. |
| [FastKernels, 2605.23215](https://huggingface.co/papers/2605.23215) | Production-aligned GPU-kernel benchmark covering 46 representative architectures in eight categories and integrating with inference-framework interfaces. | GPU/kernel results depend on hardware, compiler stack, framework compatibility, and numerical correctness; specialized coverage does not transfer to general repository optimization. | Require benchmark-production alignment, integration tests, and correctness checks for accelerator backends; do not optimize isolated kernels against synthetic inputs alone. |
| [An Agentic Evaluation Framework for AI-Generated Scientific Code in PETSc, 2603.15976](https://huggingface.co/papers/2603.15976) | PETSc/HPC code evaluation with compile/execute gates, a 14-evaluator pipeline, and five categories: correctness, performance, code quality, algorithmic appropriateness, and library-specific conventions. | Several quality dimensions use LLM judgments; the six-problem suite is domain-specific and scores only gate-passed attempts. | Keep deterministic gates first, then measure performance and evaluate library/domain conventions separately. Domain-specific semantics need their own adapters. |
| [DependEval, 2503.06689](https://huggingface.co/papers/2503.06689) | Repository dependency recognition, construction, and multi-file editing over 15,576 repositories and eight languages. | Dependency understanding is not performance evidence; repository collection and task construction introduce distribution bias. | Treat dependency/caller discovery as a separate context stage that can feed a performance investigation, not as an optimization score. |

### Additional empirical and learned-optimization evidence

These papers add two pieces missing from a syntax-first scanner: how to find
inputs that actually expose a performance problem, and how to keep learned
optimization claims tied to reproducible measurements. They are useful for
validation design, but their synthetic or competitive-programming settings
should not be mistaken for repository-wide evidence.

| Work | Granularity and method | Assumptions or failure modes | Directly applicable idea |
| --- | --- | --- | --- |
| [Language Models for Code Optimization: Survey, Challenges and Future Directions, 2501.01277](https://huggingface.co/papers/2501.01277) | Systematic review of more than 50 primary studies, organized around techniques, evaluation practices, and open challenges. | The survey describes a field with limited cross-language and cross-workload generalization and recurring trust/evaluation problems; its conclusions summarize heterogeneous studies rather than providing a new oracle. | Treat generalization, reproducibility, and trust as evaluation dimensions. Keep language, workload, and metric coverage visible instead of reporting one universal optimizer score. |
| [WEDGE / Synthesizing Performance Constraints for Evaluating and Improving Code Efficiency, 2505.23471](https://huggingface.co/papers/2505.23471) | Synthesizes branch-level performance constraints, partitions execution space into performance regions, and guides coverage-based fuzzing toward stressing inputs; releases [PerfForge](https://github.com/UChiSeclab/perfforge). | Performance is often controlled by local predicates, not input length alone. Generated tests can still miss external effects and depend on the contract and instrumentation used to generate them. | Generate adversarial workload families from path predicates and contrastive behavior, not only “largest input” fixtures. Store the stress constraint and the reason a test is expected to distinguish candidates. |
| [COFFE: A Code Efficiency Benchmark for Code Generation, 2502.02827](https://huggingface.co/papers/2502.02827) | 398 function-level and 358 file-level problems; contract-guided stressful tests; CPU-instruction-count `efficient@k`; repeated measurements with outlier removal. | Instruction count is a useful controlled-machine signal but is not wall-clock time, I/O cost, cache behavior, or energy. The reported low instruction-count variance and high time correlation are results from the paper's setup, not universal guarantees. | Preserve both a stable low-level cost signal and end-to-end wall time. Use repeated measurements, explicit warmups/outlier rules, and separate function-level from file-level evaluation. |
| [LOOPerSet: A Large-Scale Dataset for Data-Driven Polyhedral Compiler Optimization, 2510.10209](https://huggingface.co/papers/2510.10209) | 28 million labeled points from 220,000 synthetic polyhedral programs, mapping semantics-preserving loop transformations such as fusion, skewing, tiling, and parallelism to measured execution time. | The polyhedral subset has strong regularity and does not represent dynamic dispatch, I/O, frameworks, or repository semantics. Synthetic scale can improve a cost model without improving its transfer to services. | Keep compiler-style transformation learning as a separate backend and evaluate transfer to real repositories before using it for general-purpose recommendations. |
| [PerfCoder: Large Language Models for Interpretable Code Performance Optimization, 2512.14018](https://arxiv.org/abs/2512.14018) | Fine-tunes models on curated optimization trajectories with human-readable strategy annotations and runtime-based preference optimization; evaluates on the PIE performance benchmark. | The result depends on the PIE task distribution, the quality of trajectories, and the measurement loop. Interpretable strategy text is not a proof of semantic equivalence or workload coverage. | If learned ranking is explored later, retain the proposed strategy, source location, runtime evidence, and correctness outcome as separate artifacts; do not let generated explanations stand in for proof. |
| [Leveraging Reinforcement Learning and Large Language Models for Code Optimization, 2312.05657](https://huggingface.co/papers/2312.05657) | Uses unit-test and runtime feedback to train a smaller CodeT5/RRHF-based optimizer and evaluates on PIE using optimization-quality and speedup metrics. | Feedback-driven training can optimize to the available tests and benchmark distribution; shorter training or smaller models does not imply repository-level correctness or better production behavior. | Runtime feedback belongs inside a correctness-gated loop, with held-out workloads and anti-overfitting tests kept separate from the training/evaluation feedback. |
| [Not All Code Is Equal: A Data-Centric Study of Code Complexity and LLM Reasoning, 2601.21894](https://huggingface.co/papers/2601.21894) | Studies structural complexity using cyclomatic complexity and logical lines of code as controlled fine-tuning dimensions; reports that restricting data to a structural-complexity range outperformed structurally diverse data in 83% of experiments. | Structural complexity measures control-flow/compositional difficulty for model training; it is not a measurement of runtime, memory, or an algorithmic bound. The result concerns LLM reasoning rather than repository optimization. | Keep maintainability/model-facing complexity metrics separate from algorithmic and measured performance fields. A high cyclomatic score can motivate review without implying an O(n^2) hotspot. |

## Synthesis

The literature supports a layered evidence model:

1. **Static candidate:** an AST or text pattern implies a possible repeated
   scan, recursion, allocation, or I/O boundary. This is a lead, with syntax
   evidence and assumptions.
2. **Theoretical estimate:** a reviewer or symbolic analysis derives a bound
   under stated input-size and data-structure assumptions. This can explain a
   transformation but is not a workload measurement.
3. **Empirical scaling:** controlled input growth produces a fitted curve or a
   ratio across sizes. The report must include residuals, repetitions, and
   uncertainty.
4. **Practical impact:** repository workloads, profiling, database/network
   timings, rendering traces, or production-like tests establish whether the
   candidate matters on the path users actually exercise.
5. **Acceptance evidence:** behavior-equivalence checks pass and the measured
   improvement is repeatable on the declared environment.

The current skill stops at layer 1 and asks the agent to supply the other layers
manually. Its largest research gap is therefore not another pattern regex; it is
the missing bridge from a syntax-level lead to a reproducible workload and
confidence-bearing report.

## Cross-source conclusions

Three conclusions survive the comparison of formal analysis, tooling, and
repository-level benchmarks:

1. **Use a capability ladder, not a single score.** Syntax and structural
   matching are cheap and broad; type/data-flow inference is narrower; formal
   bounds are narrower still; measurements establish observed behavior for one
   workload and environment. Each layer should report its own assumptions.
2. **Localizing the right path is as important as suggesting the right edit.**
   SWE-fficiency's function-level attribution result and ISO-Bench's
   “lucky-win” quadrant both argue for separate target-identification evidence.
   A candidate should include callers, workload coverage, and the path from
   entrypoint to the suspicious operation.
3. **Validation must be adversarial and multi-objective.** Anchor verification
   protects functional behavior; FormulaCode-style workload families expose
   regressions on neighboring cases; PERFOPT-Bench-style audit protects against
   benchmark-specific shortcuts. These checks are complementary, not
   interchangeable.

The resulting research priority is a report/evidence redesign, followed by one
small executable workload protocol. Formal bound analysis and learned
optimization recommendations should remain optional experiments until the
scanner has enough labeled and repository-level evidence to evaluate them.
